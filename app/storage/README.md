Хранилище A4

`Storage(Settings().data_dir)` предоставляет платформе сохранение проектов, неизменяемых версий брифа и сущностей, запусков, заданий, артефактов, контрольных точек и использования. При старте FastAPI экземпляр доступен как `application.state.storage`. Подключения SQLite открываются на отдельную операцию и закрываются после транзакции; один экземпляр можно использовать из разных потоков.

1. **Что является основными данными.**

| Расположение внутри APP_DATA_DIR | Назначение |
|---|---|
| `state.sqlite3` | Основные данные: проекты, версии брифа, Run, лимиты, задания, архив сущностей и артефактов, Usage, полное содержимое результатов и контрольных точек |
| `results/<sha256>.json` | Дисковые копии структурированных StageResult |
| `checkpoints/<sha256>.json` | Дисковые копии контрольных точек с контекстом и состоянием графа |
| `worker.lock` | Постоянный файл блокировки единственного исполнителя; его наличие само по себе не означает занятого исполнителя |

Версия схемы базы хранится в `PRAGMA user_version`; сейчас это 4. A5 добавляет `run_inputs`; A6 — `commands` и `exports`; A8 — `external_calls` с резервами попыток, `response_cache` с проверенными ответами и `run_events` с безопасными событиями. Базы версий 1, 2 и 3 обновляются транзакционно без удаления данных. Неизвестная версия отклоняется без сброса данных. Дополнительных Python-зависимостей нет: используется стандартный `sqlite3`.

Контрольная точка содержит родительский checkpoint, задание, версию брифа, подтверждённый этап и его outcome, следующий этап, статус, качество, DataBundle, артефакты, вопросы и `graph_state`. Последний параметр предназначен для состояния оркестратора, например счётчиков исправлений. Маршрут и содержимое этого состояния выбирает платформа. [Оркестратор A5](../workflow/README.md) использует этот интерфейс для полного графа и сохранения лимита исправлений.

`Run.checkpoint_id` указывает на последнюю подтверждённую точку. После успешного шага `Run.stage` содержит следующий этап, а `checkpoint.stage` — только что сохранённый. Для ожидания ввода, ошибки и конечного результата сохраняется текущий этап. Подтверждённый ответ `needs_input` или `failed` также образует контрольную точку: его вопросы, частичные данные и ошибка не теряются.

2. **Порядок выполнения и сохранения.**

```python
from app.config import Settings
from app.storage import Storage

storage = Storage(Settings().data_dir)
project = storage.create_project("Мой продукт", brief_input)  # BriefInput из A1
run = storage.create_run(project["id"], limits)              # Limits из A1

with storage.worker() as worker:
    run = worker.claim_run(run["id"])
    job = worker.begin_step(run["id"], expected_revision=run["revision"])
    # Здесь A5 вызывает этап участника 2 и получает StageResult.
    # Во время внешнего вызова SQLite-транзакция не удерживается.
    checkpoint = worker.commit_step(
        job["id"], stage_result,
        next_stage="research", status="running", quality="draft",
        graph_state={"repair_cycles": 0},
    )
    # Только после успешного commit_step можно начинать следующий шаг.

snapshot = storage.get_snapshot(run["id"])
```

Это пример использования интерфейса, а не готовый исполнитель: `brief_input`, `limits` и `stage_result` передаёт вызывающий код. Форматы и примеры — в [контрактах](../../contracts/README.md).

Платформа проверяет StageResult по схеме, принадлежность проекту/запуску/этапу, версии, ссылки и зависимости, зарегистрированные Usage и согласованность outcome со статусом. `suggested_next_stage` агента не управляет запуском: фактический `next_stage` передаёт оркестратор. Проверки блокирующих замечаний и текущего отчёта действуют при `quality="ready"`; смысловые проверки стратегии остаются ответственностью агентов и критика.

Входящий `StageResult.data` объединяется с подтверждённым контекстом по типу и ID: пустая коллекция не удаляет предыдущие данные. Новое содержимое того же ID требует следующей версии; прежние версии остаются в архиве. Изменившиеся ссылки делают прежние артефакты и их зависимости stale в текущем снимке. Новый артефакт не может ссылаться на устаревший контекст. Исходные метаданные архива неизменяемы, текущую актуальность следует читать из Snapshot. `get_entity(project_id, kind, id, version)` и `get_artifact(project_id, id, version)` возвращают архивные версии. [A7](../workflow/INTERVENTION.md) добавляет проверенное повторное использование с новыми версиями и архивным `reused_from`; полный пересчёт остаётся резервным вариантом.

Все записи завершения шага — сущности, артефакты, checkpoint, новое состояние Run и завершение задания — входят в одну транзакцию `BEGIN IMMEDIATE`. Для SQLite включены foreign keys и `synchronous=FULL`. JSON-копии записываются через временный файл, `fsync`, атомарную замену и синхронизацию каталога до фиксации базы. Ошибка записи откатывает всю транзакцию. Следующий шаг не запускается, пока предыдущее задание остаётся выполняющимся.

При обрыве до COMMIT на диске могут остаться лишние файлы; они не считаются результатами, пока на них не ссылается база. Каталоги не используются для обнаружения результатов. `checkpoint_files(checkpoint_id)` возвращает пути и восстанавливает потерянные или повреждённые копии из SQLite. Удаление либо повреждение самой базы этим механизмом не исправляется.

Повтор `commit_step` для того же задания с тем же результатом и параметрами возвращает прежнюю контрольную точку. Изменённый повтор отклоняется. Проверка повторного завершения выполняется до проверки текущей ревизии, поэтому потерянный ответ можно безопасно перечитать даже после перехода к следующему шагу. Это идемпотентность хранения; для HTTP-команд A6 отдельно использует `Idempotency-Key` и `Storage.command`.

3. **Один исполнитель и восстановление.**

Контекст `storage.worker()` удерживает неблокирующий эксклюзивный `flock` на всё время исполнения, включая внешние вызовы. Второй процесс или второй экземпляр в том же процессе получает `WorkerBusy`. Уникальные индексы SQLite дополнительно запрещают второй активный Run, второе выполняющееся задание и второй незавершённый Run одного проекта. Другие проекты могут стоять в очереди.

Контекст worker нельзя передавать другому процессу или использовать после закрытия. Файл `worker.lock` нельзя удалять или заменять во время работы. Освобождается блокировка дескриптора, а не существование файла. Для запуска используйте Linux/macOS или Linux-контейнер с одним общим локальным каталогом/томом данных. Сетевая файловая система и распределённое выполнение не поддерживаются.

При получении блокировки новый исполнитель переводит оставшиеся `running`/`pause_requested` в `paused`, а незавершённые задания — в `interrupted`. Подтверждённые checkpoint и данные сохраняются. `queued`, `waiting_for_input`, `completed`, `failed` и `incomplete` сами по себе не меняются.

FastAPI при старте вызывает `recover_if_idle()`: восстановление происходит только при свободной блокировке. Запуск второго HTTP-процесса не прерывает живого исполнителя. Конец контекста worker освобождает блокировку; если вызывающий код оставил Run активным, следующий владелец восстановит его в paused.

Явное продолжение остановленного после сбоя запуска:

```python
run = storage.get_run(run_id)
storage.requeue_paused(run_id, expected_revision=run["revision"])
with storage.worker() as worker:
    run = worker.claim_run(run_id)
    checkpoint = storage.get_checkpoint(run["checkpoint_id"]) if run["checkpoint_id"] else None
    # A5 восстанавливает graph_state, использует сохранённые данные и начинает Run.stage.
```

Незавершённый внешний запрос после сбоя может повториться. Гарантии «вызвать провайдера ровно один раз» нет. Для нового вызова нужен новый `call_id`; завершённые ранее шаги повторять не требуется. Если процесс погиб после ответа провайдера, но до регистрации Usage, точная стоимость этого запроса локально может остаться неизвестной.

4. **Использование модели и расходы.**

`Storage` реализует `UsageSink`. Вызовы модели с этим sink разрешены внутри обработчика этапа worker, где действует контроль A8. Фабрика получает ограниченный RecordingSink; автономные пробы используют JsonlUsageSink. Пример фрагмента обработчика:

```python
from app.llm import create_model
from app.llm.summary import aggregate_usage

with create_model(settings, storage) as model:
    result = model.generate(messages=messages, schema=schema, run_id=run_id, stage="brief")

summary = aggregate_usage(storage.list_usage(run_id))
```

Run должен быть создан до первого вызова. Каждое событие регистрируется своей транзакцией сразу после попытки; откат результата этапа не отменяет уже возникшие расходы. Одинаковый event ID с тем же содержимым записывается один раз. Иное содержимое с тем же ID или повтор `(run_id, call_id, attempt)` под другим ID отклоняется. StageResult передаёт только ссылки `usage_ids` и ничего повторно не начисляет.

A8 связывает Usage с заранее сохранённым резервом в той же транзакции. Неучтённый резерв после сбоя удерживает квоту и денежную оценку. Cache hit имеет нулевую новую стоимость и проверенную ссылку cache_origin_id. Инструменты подключаются через `context.tool_call`, который владеет резервом, повторами и Usage; транспорт не должен начислять их второй раз. [Подробности A8](../workflow/RUNTIME.md).

Автономные скрипты проверки A3 продолжают использовать JSONL: это отдельные пробы, а не запуски платформы. Их журналы автоматически в SQLite не импортируются.

5. **Границы A4 и проверки.**

`append_brief` сохраняет новую неизменяемую версию между запусками; если есть незавершённый Run, операция отклоняется. В A5 добавлены `submit_answers`, `submit_selection`, `list_inputs` и выбор следующего queued-запуска. Ответ или выбор и переход waiting_for_input → queued сохраняются одной транзакцией с проверкой ревизии. Вопросы подтверждённой точки остаются в истории, но исчезают из текущего Snapshot после ответа.

A6 добавляет `Storage.command(scope, key, body, action)`: действие и его успешный ответ фиксируются атомарно. Вложенные операции используют соединение команды в текущем потоке через ContextVar. Ошибка откатывает всё действие и запись ключа. `Commands` в `commands.py` вызывается внутри этой обёртки: пауза, продолжение, правка брифа, исключение источника и неизменяемые выгрузки. Правка создаёт контрольную точку с пустым новым контекстом и stale-историей; архив и Usage сохраняются. [HTTP-интерфейс и ограничения A6/A7](../api/README.md).

A7 сохраняет план повторного использования, ключ входов и исходное время результата в `graph_state`; новая миграция базы не требуется. `interrupt_step` атомарно останавливает задание на границе внешнего действия, сохраняя подтверждённый checkpoint. Повторно используемый результат проходит обычный `commit_step`; происхождение `reused_from` проверяется по архиву.

```bash
.venv/bin/python -E -m pytest tests/test_storage.py tests/test_backend.py -q
```

Проверки принудительно завершают отдельный процесс через SIGKILL как во время следующего этапа, так и внутри транзакции его сохранения. Восстановление выполняется другим интерпретатором Python. Дополнительно проверяются конкуренция, версии, файлы, ошибки записи, история, вопросы, расходы и откаты. Реальные модели и сеть не используются. [Протокол A4](../../project-notes/reports/A4_CHECKS.md).

Для резервной копии остановить приложение и worker, затем скопировать весь APP_DATA_DIR. Данные защищены правами пользователя и исключениями Git, шифрование на диске не добавлено. Устойчивость к физическому отказу носителя или нарушению гарантий `fsync` не проверялась.

При реализации сверены официальные описания [транзакций SQLite](https://www.sqlite.org/atomiccommit.html), [модуля sqlite3 Python 3.12](https://docs.python.org/3.12/library/sqlite3.html) и [fcntl/flock](https://docs.python.org/3.12/library/fcntl.html).
