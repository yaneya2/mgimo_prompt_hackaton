Управление выполнением A7

Платформа сохраняет запрос паузы, проверяет его перед внешними действиями, версионирует правки брифа и повторно использует подходящие подтверждённые результаты. Управление доступно через [HTTP API](../api/README.md). Модель и поиск в синтетических проверках не вызываются.

1. **Пауза между действиями.**

API переводит выполняющийся Run в `pause_requested`. Уже начатый запрос может завершиться; его Usage сохраняется. Перед следующим внешним действием проверяется состояние SQLite. Адаптеры OpenRouter и Codex проверяют его непосредственно перед запросом/запуском процесса, OpenRouter — также перед повторной попыткой. Сигналы остановки worker используют тот же механизм.

Инструменты участника 2 должны вызывать `context.check_pause()` непосредственно перед каждым Search, Extract, чтением файла и другим внешним действием. Для функций, которым StageContext не передаётся, доступен `app.execution.before_external_action(run_id)`. Пример:

```python
def research(request, context):
    context.check_pause()
    candidates = search(query)
    context.check_pause()
    sources = extract(candidates)
    # Сформировать и вернуть StageResult.
```

`PauseRequested` — сигнал управления, его нельзя преобразовывать в ошибку поиска/модели или подавлять общим `except Exception`. Оркестратор перехватывает сигнал и одной транзакцией помечает текущее задание interrupted, а Run — paused. Подтверждённая контрольная точка остаётся прежней, ошибка выполнения не создаётся. Resume возвращает тот же Run в очередь и повторяет незавершённый этап. Завершённые предыдущие этапы не запускаются повторно.

Обработчики и инструменты работают синхронно в потоке worker. Контроль передаётся через ContextVar, поэтому произвольные дочерние потоки/процессы внутри обработчика не поддерживаются. Самодельный инструмент, который не вызывает проверку, остановится только на границе этапа. При интеграции `LizaLiza` проверки нужно добавить перед транспортом `ResearchTools._post` и чтением `ResearchTools.read_file`; этот код пока находится в другой ветке.

При завершении последнего этапа пауза может закончиться completed, при появлении вопроса — waiting_for_input. Если пользователь приостановил уже ожидающий ввод Run, resume восстанавливает сохранённые вопросы без повторного вызова агента.

Ограничение: результат незавершённого этапа не является подтверждённой контрольной точкой. При продолжении могут повториться и уже завершившиеся внешние запросы внутри этого этапа; их предыдущие Usage сохраняются и новые попытки учитываются отдельно. Кэш отдельных внешних запросов здесь не реализован. Текущий внешний запрос не прерывается принудительно; после SIGKILL его точная оплата может остаться неизвестной, если Usage ещё не сохранён.

2. **Карта B7 и повторное использование.**

Основание — таблица B7 в `docs/participant-2.md` ветки `LizaLiza`, коммит `8731ec7`. В платформе её консервативная граница задана в `app/reuse.py`:

| Изменение | Обязательно пересчитать начиная с |
|---|---|
| Продукт, допущения, неизвестные | brief |
| Цель, аудитория, исключённые источники | research |
| Бюджет, горизонт, ограничения/запрещённые каналы | options; research также пересчитывается, если зависящие от него входы изменились |

После каждой правки brief выполняется снова для проверки нового ввода и обновления его происхождения. Прежние артефакты остаются в истории как stale. Этапы до указанной границы могут быть восстановлены из подтверждённых результатов только после проверки зависимостей; остальные выполняются заново. Selection и report всегда требуют нового прохода: прежний выбор человека не переносится автоматически.

По умолчанию этап **не разрешает повторное использование**. Его автор должен явно описать все поля брифа и коллекции данных, от которых зависит результат:

```python
StageSpec(
    handler=research,
    prompt_version='research-v2',
    model_id='точный-идентификатор-модели',
    reuse_brief_fields=('product', 'goal', 'audience', 'assumptions', 'unknowns', 'excluded_source_ids'),
    reuse_collections=('capabilities', 'sources', 'claims', 'issues'),
    reuse_max_age_seconds=3600,
)
```

Это пример интерфейса, не готовое разрешение для реального исследователя. Если его исследовательские вопросы зависят от бюджета, сроков или ограничений, соответствующие поля обязательно включить в `reuse_brief_fields`; пока это не проверено, оставлять значения `None`. Источники, применимость которых нельзя подтвердить по сохранённому контексту, читать заново. В demo зависимости описаны только для синтетического research. Реальные этапы из другой ветки автоматически это разрешение не получают.

Помимо декларации проверяются:

- Успешное завершение исходного этапа и наличие его артефактов в текущем контексте перед правкой; неполные, ошибочные и уже устаревшие результаты не подходят.
- Совпадение значимых входов, резюме и состава текущих входных артефактов, ответов человека, замечаний и счётчика исправлений. Смена только технических версий не меняет содержательный ключ. Для заново сформированного user_text-брифа допускается другая дата создания оболочки при идентичном содержимом.
- Точные версии модели, промпта и декларации зависимостей. Смена манифеста требует нового Run; старые манифесты A5/A6 без деклараций продолжают работать, но их старые результаты повторно не используются.
- Возраст результата и прочитанных внешних/файловых источников. По умолчанию — до часа; можно задать положительное число секунд до 86400. Повторное использование не обновляет исходное время и не продлевает срок цепочкой правок. Это ограничение возраста, а не подтверждение, что внешний документ не изменился.

Совпавший результат проходит обычную проверку схемы и связей. Для сущностей и артефактов создаются следующие неизменяемые версии текущего брифа. Evidence, ReviewIssue.target, EntityRef и зависимости артефактов переводятся на точные новые версии. Тексты и дата чтения источника сохраняются. Старые записи не редактируются.

В Artifact добавлено необязательное `reused_from: {artifact_id, version, brief_version}` — ссылка на исходный архивный результат. Поле создаёт только платформа; агент не может выдать свой результат за повторно использованный. Клиент может показывать по нему отметку. Это историческая ссылка, а не current-зависимость `depends_on`. Новый Usage не создаётся, прежние расходы остаются в запуске. Резервный renderer показывает происхождение повторно использованных этапов.

3. **Восстановление и воспроизведение.**

План пересчёта, кандидаты, ключи входов и происхождение сохраняются в контрольных точках SQLite. Отдельного кэша в памяти процесса нет. При перезапуске worker восстанавливает незавершённые задания в paused, а подтверждённые результаты и бюджет использованных исправлений сохраняются. Исторические выгрузки неизменяемы.

Запустить API и demo-worker по [инструкции](../api/README.md), затем:

```bash
.venv/bin/python -E -m scripts.try_api --revise-budget
```

Сценарий создаёт проект с бюджетом 50000 RUB, доходит до выбора, меняет бюджет на 12000 RUB и запрещает платную рекламу, явно продолжает Run, проверяет повторное использование research, снова имитирует выбор человека и скачивает черновик. Итог и снимок находятся в `data/api-checks/<run_id>/`. Это проверка управления синтетическими этапами, не содержательной адаптации стратегии настоящей моделью.

Автоматическая проверка этого сценария запускает отдельные процессы API и worker, останавливает их, затем проверяет Snapshot и побайтное содержимое выгрузок новым сервером. Также сохранены проверки SIGKILL прежних этапов A4/A5. [Протокол A7](../../project-notes/reports/A7_CHECKS.md).

Независимая приёмка через экраны C3/C5 и интеграция инструментов/деклараций реальных агентов ещё предстоят. Кэш отдельных запросов и централизованное ограничение расходов относятся к A8.
