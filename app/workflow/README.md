Оркестратор и worker A5

Реализован граф `brief → research → options → communications → review → selection → report`. Worker запускается отдельным процессом, читает очередь SQLite и сохраняет результат каждого шага до следующего вызова. Перезагрузка интерфейса и остановка HTTP-сервера не управляют его жизненным циклом.

В репозитории есть полный синтетический набор этапов и интерфейс подключения функций участника 2. Реальные B1–B6 ещё не предоставлены. Синтетический прогон не вызывает модели или поиск, не подтверждает факты и завершается с `quality=draft`, даже при техническом `status=completed`.

1. **Проверить весь путь одной командой.**

```bash
.venv/bin/python -E -m scripts.try_workflow
```

Скрипт создаёт новый тестовый проект в отдельном каталоге `data/workflow-checks`, запускает worker в трёх новых процессах и имитирует два действия человека: ответ о бюджете и выбор первого варианта. Между этапами данные не копируются вручную. Итоговый JSON-снимок сохраняется в этом каталоге; путь печатается в терминале. Ожидается `completed`, `draft`, 9 заданий и 0 событий использования.

Другой тестовый продукт:

```bash
.venv/bin/python -E -m scripts.try_workflow --product "Условный сервис учёта расходников мастерской"
```

Это проверка переносимости платформенного сценария; она не доказывает качество стратегии для нового рынка. В обычном worker автоматического ответа или выбора нет — они реализованы только в демонстрационном скрипте.

2. **Запустить worker и управлять своим запуском.**

Для тестовых этапов выбор должен быть явным:

```bash
.venv/bin/python -E -m app.worker --stages demo
```

`--once` обрабатывает доступные queued-запуски до завершения, ошибки или ожидания ввода и выходит, когда очередь пуста. Без него worker опрашивает очередь каждые `APP_WORKER_POLL_SECONDS` (по умолчанию 0,5 секунды). `--data-dir` переопределяет APP_DATA_DIR. Все процессы одного сценария должны использовать один каталог данных.

До реализации HTTP API A6 доступны локальные команды:

```bash
.venv/bin/python -E -m app.workflow create --name "Мой проект" --brief brief.json
.venv/bin/python -E -m app.workflow status RUN_ID
.venv/bin/python -E -m app.workflow answers RUN_ID --revision REVISION --file answers.json
.venv/bin/python -E -m app.workflow select RUN_ID --revision REVISION --option OPTION_ID --version OPTION_VERSION --rationale "Причина выбора"
.venv/bin/python -E -m app.workflow resume RUN_ID --revision REVISION
```

Заменить RUN_ID, REVISION, OPTION_ID и OPTION_VERSION актуальными значениями из `status`. `brief.json` содержит объект BriefInput из [контрактов](../../contracts/README.md), без внешней обёртки. `answers.json` — массив `[{"question_id":"question_budget","value":"Бюджет пока неизвестен"}]`. Значения и ID вопросов нужно брать из своего снимка. `create --limits limits.json` принимает отдельный объект Limits; по умолчанию передаются 20 вызовов модели, 10 поисковых вызовов, 2 исправления, timeout 120 секунд и неизвестный денежный бюджет.

В A5 оркестратор обеспечивает лимит исправлений. Число модельных/поисковых вызовов, денежный бюджет и timeout передаются обработчикам; централизованное обеспечение всех лимитов относится к A8. Адаптер A3 продолжает применять собственные сетевые тайм-ауты и ограниченные повторы. Произвольную синхронную функцию worker принудительно по таймеру не прерывает.

Ответы принимаются только в waiting_for_input, для существующих вопросов, без дубликатов и с заполнением всех обязательных полей. Выбор допустим только на этапе selection, для текущих ID и версии варианта с актуальным артефактом. Операция сохраняет ввод и переводит Run в queued одной транзакцией. Неверная ревизия или повтор команды после смены состояния отклоняется. HTTP Idempotency-Key предстоит добавить в A6.

`resume` предназначен для paused после остановки или сбоя. Автоматического возобновления paused, failed или incomplete нет. Полное пользовательское управление и политика повторного запуска относятся к A7–A8.

Для Docker добавлен необязательный профиль `worker`, использующий тот же том `/data`. Указать `APP_STAGE_FACTORY=demo` в `.env` для синтетической проверки либо фабрику реальных этапов, затем:

```bash
docker compose --profile worker up --build -d
docker compose logs --tail=100 worker
```

HTTP-проверка здоровья контейнера backend не применяется к worker. Включён период мягкой остановки контейнера 330 секунд; после него Docker может принудительно завершить процесс. Внутри текущего образа доступен OpenRouter, а локальный Codex хоста не установлен.

3. **Подключить реальные функции участника 2.**

Настройка `APP_STAGE_FACTORY=app.agents.registry:build_stages` указывает на доверенный модуль приложения. Путь задаёт оператор, он не берётся из текста брифа или ответа модели. Если настройка не указана, worker завершится с сообщением конфигурации, а не начнёт тестовую генерацию автоматически.

Модуль фабрики должен вернуть реестр шести функций. Например, после реализации соответствующих модулей:

```python
from app.workflow import StageRegistry, StageSpec
from app.agents import brief, research, options, communications, review, report

def build_stages(settings, usage_sink):
    handlers = {
        "brief": brief.run,
        "research": research.run,
        "options": options.run,
        "communications": communications.run,
        "review": review.run,
        "report": report.run,
    }
    return StageRegistry(
        name="agents-v1",
        stages={name: StageSpec(handler, prompt_version=name + "-v1",
                                model_id=settings.model_name or "provider-default")
                for name, handler in handlers.items()},
    )
```

Это интерфейс подключения; указанных `app.agents.*` пока нет. Фабрика получает Settings и узкий UsageSink с методом `record`, без методов записи запусков. Для своих вызовов она может создавать адаптер через `create_model(settings, usage_sink)` и регистратор инструментов `UsageRecorder(usage_sink)`. Внешние клиенты нужно закрывать в коде обработчика, например через `with create_model(...)`. Для явной передачи зависимостей используйте замыкания или объекты с `__call__`.

Каждая синхронная функция имеет сигнатуру `handler(request: dict, context: StageContext) -> dict`:

| Вход | Содержание |
|---|---|
| request | StageRequest A1: текущий бриф, объединённый DataBundle, метаданные артефактов с freshness, Limits, версии промпта и модели |
| context.inputs | Сохранённая история ответов и выбора с исходными вопросами, этапом, версией брифа и checkpoint_id; использовать релевантные ответы, не путать их с внешними фактами |
| context.feedback | Безопасные коды причины повторного вызова, например INVALID_STAGE_RESULT |
| context.repairs_used | Число уже израсходованных исправлений всего запуска |
| context.synthetic | Явный признак тестового реестра |

Выход — StageResult A1. Успешный этап должен вернуть хотя бы один артефакт своего этапа и правильную prompt_version. Повтор изменённого объекта/артефакта требует новой версии. На options должны появиться хотя бы три ID вариантов; содержательную различимость проверяет критик. Ответы, варианты, источники и утверждения не добавляются платформой к реальному результату за агента.

`selection` принадлежит платформе и не регистрируется как агент. Она запрашивает выбор, создаёт Decision с `author=user` только из сохранённого действия человека и передаёт управление report. Агент не может создать или изменить такое решение. Итог не может подменить выбранную версию варианта. Функция report должна собрать документ из полученных данных; сохранённый StageResult и его артефакт становятся входом renderer/выгрузки A6.

Имя реестра, synthetic, версии промптов и модельные идентификаторы сохраняются в graph_state. После первой точки продолжение с другим манифестом завершается failed/INVALID_STATE до вызова функции. Разработчик должен менять версии при изменении поведения: исходный код функций автоматически не хешируется. `model_id` в запросе обозначает настроенную модель/алиас; фактическая модель вызова и использование сохраняются адаптером A3.

4. **Переходы, исправления и ошибки.**

Обычный success следует фиксированному графу. `suggested_next_stage` — только данные агента; он не позволяет пропустить критика или выбор. `needs_input` сохраняет вопросы и освобождает очередь для других проектов. `failed` и `incomplete` сохраняют частичный результат и останавливают Run.

Критик с needs_revision или неустранёнными блокирующими замечаниями возвращает процесс в research, options или communications по ReviewIssue.return_to. Если направлений несколько, выбирается наиболее раннее. Затем снова выполняются зависимые этапы и review. `accepted_limitation` не снимает блокировку. Если у критика нет допустимого маршрута исправления, сохраняется incomplete/blocked с объяснением.

Для needs_revision на другом этапе повторяется этот этап. Исправления формата и возвраты критика расходуют общий `Limits.max_repair_cycles`, записанный в контрольной точке. Перезапуск не сбрасывает счётчик. При исчерпании лимита сохраняются incomplete/blocked, диагностический артефакт и `graph_state.stop_reason`.

Невалидный ответ не сохраняется как данные предметной области и не передаётся дальше. Сначала атомарно сохраняется диагностическая контрольная точка, затем возможен повтор с кодом причины. Текст приватного ответа или исключения в диагностику не копируется. Уже зарегистрированный Usage остаётся в базе независимо от отката ответа. Ошибка самого хранилища останавливает worker и не запускает следующий внешний вызов.

Итог real-реестра получает ready только при текущем отчёте, неизменённом выборе человека и отсутствии блокирующих замечаний/сообщений. Это структурная проверка платформы; истинность и содержательное качество требуют реальных агентов и независимой приёмки. Demo остаётся draft.

5. **Остановка, восстановление и проверки.**

Ctrl+C/SIGTERM ставит флаг остановки: текущая синхронная функция завершается, результат сохраняется, следующий этап не начинается, активный Run переходит в paused. Если этап уже завершил весь запуск или запросил ввод, его конечный статус сохраняется. При SIGKILL новый worker восстанавливает прерванное задание по правилам [A4](../storage/README.md); для продолжения нужна команда resume. Завершённые этапы не повторяются, незавершённый внешний вызов может повториться.

```bash
.venv/bin/python -E -m pytest tests/test_workflow.py tests/test_storage.py -q
.venv/bin/python -E -m pytest -q
```

Проверяются весь граф и пользовательские границы, маршруты критика, исчерпание лимита, невалидные ответы, ошибки провайдера/диска, переход версии базы 1 → 2, независимый процесс worker, SIGTERM, SIGKILL и продолжение с research без повторения brief. [Протокол A5](../../project-notes/reports/A5_CHECKS.md).

При обработке сигналов использованы рекомендации [Python signal](https://docs.python.org/3.12/library/signal.html): обработчик меняет простой флаг, не пишет в SQLite и не захватывает блокировки.
